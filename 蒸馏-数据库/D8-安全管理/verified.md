## C1 两种身份验证模式 —— 通过

**V1① 书中原表述**（§11.1.1，OCR 已修）：两种验证方式——Windows 验证方式（完全采用 Windows 服务器的验证，只要能登录 Windows 服务器的用户就可登录 SQL Server 2012）与 Windows 和 SQL Server 混合验证方式（不但允许 Windows 用户登录，也允许独立的 SQL Server 用户登录；没有 Windows 账号或用其他操作系统通过网络连接的人也可登录）。修改验证模式：SSMS→右键服务器→属性→安全性→选择验证方式；改后必须停止再重启 SQL Server 服务才生效。

**V1② 教学重构**：判据一句话——**是否允许"SQL Server 独立登录账号"**。只认 Windows 账号=Windows 模式；放行 SQL Server 自建账号=混合模式。混合更灵活（非 Windows 用户、无 Windows 建号权限的管理员都能自建账号）。

**V2 新题**：某外包人员用 macOS 通过网络访问公司 SQL Server，服务器应采用哪种验证模式？为什么？
自答：混合验证。Windows 验证只认 Windows 用户，macOS 用户没有 Windows 账号；混合验证允许独立的 SQL Server 登录账号，非 Windows 系统通过网络也能连接。✅ 可迁移。

**V3'**：高。简答原题（练习题 1）+ 场景判断新题都可出；"改模式须重启服务"是隐藏失分点。

## C2 登录名 vs 数据库用户 两级模型 —— 通过

**V1① 书中原表述**（§11.2、§11.3.1，OCR 已修）：两类登录账户——登录服务器的登录账号（Login Name）与使用数据库的用户账号（User Name）。登录账号属服务器层面，本身并不能访问服务器中的数据库；要使用数据库必须有用户账号。用户名要在特定数据库内创建并关联一个登录名；用户信息存放在服务器的每个数据库的 sysusers 表中，用户没有密码同它相关联。一个登录账号在一个数据库中只能有一个用户账号，但可在不同数据库各有一个。登录账号对某库有访问权≠能对对象插入更新，还须设置用户账号权限。sa 是超级登录账号，安装后密码为空，装完系统首先要为它设置密码。

**V1② 教学重构**：两级门禁——登录名=大门钥匙（能进机房大楼=连上服务器），数据库用户=房间通行证（能进具体数据库的房间），权限=房间里能碰哪张桌子。有钥匙没通行证=只能在大堂站着（连得上、打不开库）。

**V2 新题**：用户反映"我能用登录名连上服务器，但打不开 student 库"，最可能缺哪一级？
自答：缺 student 库中的数据库用户账号（登录名未映射该库用户，或映射了但未授权）。两级模型：登录名管进服务器，用户账号管进数据库，权限管操作对象。✅ 可迁移。

**V3'**：高。选择（层级关系/一个登录名在一个库只有一个用户）+ 简答（练习题 2 原题）双题型；sa 密码为空是填空点。

## C3 角色：服务器角色与数据库角色 —— 通过

**V1① 书中原表述**（§11.1.2、表 11-1、§11.3.2、表 11-2，OCR 已修）：角色与 Windows 用户组概念相似，可理解为一些权限的集合。两种类型：服务器角色（负责管理与维护 SQL Server 的组，安装时定义固定服务器角色：sysadmin=可执行任何活动；serveradmin=设置服务器范围配置选项、关闭服务器；setupadmin、securityadmin=管理服务器登录/读错误日志/改密码；processadmin；dbcreator=创建更改删除数据库；diskadmin=管理磁盘文件；bulkadmin=大容量插入；public=所有用户都具有）与数据库角色（应用于单个数据库，分数据库角色和应用程序角色，应用程序角色本身不包括任何成员）。固定数据库角色 10 个：public（每个用户都属于）、db_owner（全部权限）、db_accessadmin、db_securityadmin、db_ddladmin（可发所有 DDL，但不能发 GRANT/REVOKE/DENY）、db_backupoperator、db_datareader、db_datawriter、db_denydatareader、db_denydatawriter。新用户自动加入 public。

**V1② 教学重构**：服务器角色管"楼"（服务器层，配给登录名），数据库角色管"房间"（库层，配给用户）。名单按"能干什么"记：owner 全权、accessadmin 进出门、securityadmin 发钥匙、ddladmin 改结构、backupoperator 备份、reader/writer 读写、denyreader/denywriter 显式禁读写。两个 deny 角色是"预置黑名单"。

**V2 新题**：新用户 zhang 加入数据库后未加入任何自定义角色，他至少属于哪个角色？能否让他连 public 都不属于？
自答：至少属于 public——建库时系统默认创建 10 个固定数据库角色，public 最基本，新用户添加时自动加入，不可脱离。✅ 可迁移。

**V3'**：高。固定角色名单是填空/选择常客；public"人人必有、自动加入"是判断题陷阱；应用程序角色"不含成员"是选择题陷阱。

## C4 权限三分类 —— 通过

**V1① 书中原表述**（§11.3.3 之 1，OCR 已修）：权限分为三类。①对象权限：对表、视图、存储过程等对象的操作权限——对表/视图是否允许 SELECT、INSERT、UPDATE、DELETE；对表和视图的字段是否允许 SELECT、UPDATE；对存储过程是否可 EXECUTE。②语句权限：相当于数据定义语言的语句权限——CREATE TABLE、CREATE DEFAULT、CREATE RULE、CREATE VIEW、CREATE PROCEDURE、BACKUP DATABASE、BACKUP LOG。③隐含权限：SQL Server 预定义的服务器角色、数据库所有者（dbo）和数据对象所有者拥有的权限，不需要明确授予，也不能设置（如 sysadmin 成员可在整个服务器范围做任何操作）。

**V1② 教学重构**：三分类一句话——**对"对象"动手=对象权限；发"DDL/备份"语句=语句权限；生下来就带=隐含权限**。归类型选择题的快速通道：动词落在表/视图/过程上→对象；动词是 CREATE/BACKUP→语句；sysadmin/dbo 自带→隐含。

**V2 新题**：CREATE TABLE 和对表 INSERT 各属哪类权限？BACKUP DATABASE 呢？
自答：CREATE TABLE=语句权限（DDL 类）；对表 INSERT=对象权限；BACKUP DATABASE=语句权限（书把它归入语句权限清单）。✅ 可迁移，且 BACKUP DATABASE 归"语句权限"而非"对象权限"是易错点。

**V3'**：高。简答原题（练习题 3）；对象/语句归类是选择题陷阱（尤其 BACKUP DATABASE、字段级 SELECT/UPDATE）。

## C5 GRANT/REVOKE/DENY 三动词 + 继承与 DENY 优先 —— 通过

**V1① 书中原表述**（§11.3.3 之 2/3，OCR 已修）：权限管理三内容——①授予权限：允许某用户或角色对对象执行某操作或语句；②拒绝访问：拒绝某用户或角色访问某对象，即使该用户被授予或因继承获得这种权限，仍不允许执行；③取消权限：不允许某用户或角色执行某操作。**不允许与拒绝不同**：不允许（取消）后可通过加入角色重新获得允许权；拒绝后无法再通过角色获得允许权。三种权限冲突时，拒绝访问权限起作用。用户权限继承角色的权限；用户分属不同角色时权限基本以各角色并集为准，但只要有一个拒绝，该权限就是拒绝的。（英文对应：授予=GRANT、拒绝=DENY、取消=REVOKE，英文词见书中表 11-2 db_ddladmin 行。）

**V1② 教学重构**：权限账本——GRANT=记账存入一笔"允许"；REVOKE=把这笔存入划掉（余额回零，中立足点，还能再存）；DENY=盖"冻结"章（不管之后存入多少、角色转来多少，一律冻结）。冲突裁决：DENY 一票否决。

**V2 新题**：User1 属 Role1（对表 T 的 SELECT 为 GRANT）和 Role2（对表 T 的 SELECT 为 DENY），User1 能查 T 吗？若把 Role2 的 DENY 改成 REVOKE 呢？
自答：不能查——多角色取并集但只要有一个 DENY 即拒绝。改成 REVOKE 后：Role1 的 GRANT 仍在，并集中 SELECT 为允许，能查（REVOKE 只划掉本角色的那笔，不否决其他来源）。✅ 可迁移，正中 REVOKE/DENY 区分。

**V3'**：极高。三动词辨析（尤其"取消后还能经角色再获得、拒绝后不能"）是本章第一失分点；填空（三动词+冲突裁决）+判断+应用题全覆盖。
